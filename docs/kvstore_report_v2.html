Part 1 — The Basics

1.1 What is a database, really?

A database is any program whose job is to remember data for you — reliably. That last word is the whole game. Any program can hold data in variables while it runs, but that data vanishes the instant the program exits, crashes, or the computer loses power. A database's promise is: give me your data, and I will still have it tomorrow, even if things go wrong tonight.

Databases come in many shapes. The one you have probably heard of — SQL databases like MySQL or PostgreSQL — organize data into tables with rows and columns and answer complex queries. But underneath almost every fancy database sits something much simpler, and that simpler thing is what this project builds.

You might reasonably ask: why not just write my data to a file? After all, files survive restarts too. The answer is that a plain file solves the easy half of the problem and none of the hard half. What happens if the program is killed halfway through saving? What if two threads save at once? What if the file slowly fills the disk? What if a few bytes on the disk silently go bad? A database is, at its heart, a file plus disciplined answers to all of those questions. This report is the story of those answers.

Database theory summarizes the promises a trustworthy database makes with a famous four-letter acronym:

ACID — Atomicity (an operation fully happens or not at all), Consistency (the data never enters an invalid state), Isolation (concurrent operations do not see each other's half-finished work), and Durability (finished work survives crashes). kvstore delivers atomicity and durability for every single operation, isolation between concurrent threads, and consistency of its own on-disk format. Full ACID across groups of operations — multi-key transactions — is what heavyweight databases add on top; §2.17 discusses that boundary honestly.

One more foundation before we start. Everything a computer stores — text, numbers, images — is ultimately bytes, and this report talks about bytes constantly, so let's define them once:

Bit, byte, and hexadecimal — a bit is the smallest unit of data: a single 0 or 1. A byte is 8 bits, which can represent 256 distinct values (0–255). Because binary is unreadable and decimal doesn't line up with bytes, programmers write bytes in hexadecimal (base 16, digits 0–9 then A–F): one byte is exactly two hex digits, e.g. 0x00 = 0, 0x41 = 65 (the letter 'A' in ASCII), 0xFF = 255. The 0x prefix just marks “this is hex”. A number like 0xEDB88320 is four bytes.

1.2 What is a key–value store?

Key–value store — the simplest kind of database. You hand it a key (a name, like "user_42") and a value (any data, like "Alice"). Later you give it the key back and it returns the value. It is exactly like a dictionary or a HashMap — except it survives your program closing.

Three operations cover almost everything: set (store or overwrite a key), get (look a key up), and delete (remove a key). kvstore adds a few more conveniences: keys that expire automatically after a time limit, listing keys in sorted order, and scanning a range of keys.

Why does this simple thing matter?
Because it is the foundation layer. Amazon's shopping cart, Discord's message metadata, your browser's local storage, the settings on your smart thermostat — all of these are key–value lookups at the bottom. If you understand how to build one safely, you understand the hardest 20% of what real database engines do.

Where does a key–value store sit in the wider database landscape? Think of it as a trade: a SQL database can answer “find every user in Toronto who signed up last week and joined more than three groups” — arbitrary questions over structured data — but pays for that power with query planners, indexes, and complexity. A key–value store answers exactly one kind of question — “what is the value for this key?” — and in exchange can be tiny, extremely fast, and easy to reason about. Neither is “better”; they occupy opposite ends of a power-versus-simplicity spectrum, and large systems routinely use both. (In fact, several SQL databases store their tables inside a key–value engine: MySQL's MyRocks backend and CockroachDB both sit on top of RocksDB, a key–value store.)

1.3 What does “embedded” mean?

Embedded database — a database that runs inside your own program, as a library you link against, rather than as a separate server you talk to over a network. SQLite is the most famous example: there is no “SQLite server” — the code lives inside your app and reads/writes an ordinary file.

kvstore works the same way. You write: 

kvstore::KVStore store("data/my_database.db");
store.Set("greeting", "hello world");
auto v = store.Get("greeting");   // v contains "hello world"

No server to install, no network, no configuration. The store is just a C++ object backed by files on disk. This is why embedded stores are everywhere: phones, browsers, game consoles, routers, and tiny internet-of-things devices that could never run a full database server.

1.5 What makes it interesting

kvstore is small (~700 lines), but it takes three promises seriously that toy projects usually skip:

  • Durability — once a write is acknowledged, it survives a crash or a power cut. Not “usually survives” — survives, provably, because every write is forced onto the physical disk before the store says “done”.
  • Concurrency — many threads can read and write at the same time without corrupting anything or losing updates. The data is split across 16 independent partitions so threads rarely wait on each other.
  • Bounded growth — an append-only file would grow forever; compaction rewrites it down to just the live data, safely, even while other threads are still reading.

Why are these three specifically the hard part? Because each one is invisible when it works. A store that loses data one time in a thousand crashes looks identical to a correct one in every demo. A race condition may only strike under production load, months in. A growing log file only matters after weeks of uptime. Getting these right requires reasoning about what happens at every possible instant of failure — which is exactly the discipline this report tries to teach.

Part 2 — The Core Ideas, One at a Time

This is the vocabulary-building part. Each idea below is a self-contained mini-lesson. If you read these in order, nothing in the code walkthrough will surprise you.

2.1 Memory vs. disk — the two worlds your data lives in

A computer stores data in two fundamentally different places:

  • RAM (memory) — blazing fast (nanoseconds), but volatile: everything in it is erased the moment power is lost or the process exits.
  • Disk (SSD / hard drive / SD card) — thousands of times slower (microseconds to milliseconds), but persistent: data survives power-off.

How big is the speed gap? Big enough that intuition fails. Here are rough, order-of-magnitude latencies — worth internalizing, because every database design decision traces back to this table:

Where the data isTypical access timeScaled to human time (1 ns = 1 second)

RAM~100 nanoseconds~2 minutes
SSD read~100 microseconds~1 day
SSD flush (fsync)~1 millisecond or more~2 weeks
Spinning hard disk seek~10 milliseconds~4 months

Every database is a negotiation between these two worlds. kvstore keeps a full copy of the data in RAM (a hash map, for fast reads) and a record of every change on disk (for safety). The art is in keeping the two in agreement at every instant — even the instant the power dies. And the table explains the strategy: answer every read from RAM (seconds, in scaled time), and make every write pay one trip to disk (weeks, in scaled time) — but only one, appended at the end of a file, never scattered around it.

2.2 What is a “crash”, and what is durability?

Crash — any abrupt stop: the program is killed, it hits a bug and aborts, the OS panics, or the power goes out. The defining feature is no warning and no cleanup: whatever was half-done stays half-done.
Durability — the guarantee that once the database says “your write succeeded”, that write can never be lost — not by a crash, not by a power cut. It is the “D” in the famous ACID acronym from database theory.
Why is durability hard?
Because writing to a file does not actually write to the disk. When your program calls write(), the operating system copies the bytes into a RAM cache and returns immediately — the physical disk write happens seconds later, whenever the OS feels like it. If power dies in that window, the “written” data is gone. A program that only calls write() (or C++'s ofstream::flush()) is not durable, even though it looks like it is.

To really understand this, follow one byte on its journey from your program to permanent storage. There are more way-stations than most programmers realize:

your variable (program memory) | your code assembles a record buffer v write() system call ................ byte enters the KERNEL | v OS page cache (RAM!) ............... write() RETURNS HERE — "success" | the OS flushes lazily, seconds later v disk controller's own cache ........ still volatile on cheap drives! | fsync()/fdatasync() forces BOTH of these flushes v physical medium (NAND flash / platter) <-- only NOW power-cut safe
System call — the formal doorway from your program into the operating system kernel (the privileged core of the OS that owns all hardware). Ordinary code cannot touch a disk directly; it must ask the kernel via calls like open, write, and fsync. Each call has a cost (~hundreds of nanoseconds) because the CPU switches into kernel mode and back. Page cache — the kernel's RAM staging area for file contents, organized in 4 KiB “pages”. Reads are served from it when possible; writes land in it and are flushed to the device in the background. It is why file I/O feels fast — and why “written” does not mean “safe”.

2.3 flush vs. fsync — forcing bytes onto the metal

flush — pushes bytes from your program's internal buffer to the operating system's cache. The data is now safe from your program crashing — but not from power loss, because it is still only in RAM.
fsync / fdatasync — a system call that says to the OS: “do not return until these bytes are physically on the storage device.” This is the only way to survive a power cut. fdatasync is a slightly cheaper variant that skips flushing file metadata (like the last-modified time) when only the contents matter.

kvstore calls fdatasync after every single write, before telling the caller the write succeeded. This is expensive — an fsync can take milliseconds — and it is the honest price of real durability. (Real databases offer the same trade-off: PostgreSQL's synchronous_commit, Redis's appendfsync always.)

Why is fsync so slow, when the write itself felt instant? Because it forbids every shortcut. A normal write is the OS promising to get around to it; fsync makes it actually happen, now: the kernel must locate the dirty pages, issue real commands to the device, and — critically — tell the drive to flush its own internal cache, then wait for the hardware to confirm. An SSD confirming a flush must physically program NAND flash cells, which takes on the order of a millisecond; a spinning disk must wait for the platter to rotate under the head. Datacenter hardware sidesteps this with batteries: a drive with a power-loss-protected cache can safely confirm an fsync the moment data reaches its RAM, because its capacitors guarantee the RAM will be drained to flash even if the cord is pulled. This is why the same code can run 50× faster on server hardware — the durability contract is identical; the hardware just keeps it more cheaply.

2.4 The write-ahead log (WAL) — the single most important idea

Write-ahead log (WAL) — an append-only file where every change is written before the in-memory data is updated. “Append-only” means new data is only ever added at the end; nothing in the middle is ever modified.
Record — one serialized change in the log: “set this key to this value”, “set it with an expiry”, or “delete it”. Each record is a self-contained chunk of bytes framed with its own lengths and a trailing checksum (the exact byte layout is dissected in §3.3). The log is nothing but records, one after another.

The rule is: log the intent before changing the state. Suppose you call Set("name", "Alice"). kvstore first appends a record saying “set name=Alice” to the log file and fsyncs it. Only then does it update the in-memory map. Now consider a crash at any possible moment:

  • Crash before the log write finishes — the log has a half-written record at the end; memory was never touched. On restart, recovery detects and discards the partial record. The write is cleanly lost — which is correct, because the caller was never told it succeeded.
  • Crash after the log write, before the memory update — memory is gone anyway (it is RAM). On restart, the log contains the complete record, and replaying the log rebuilds the memory state including this write.
  • Crash any time later — same as above: the log has everything; replay rebuilds everything.
Why a log instead of just saving the map to a file?
Two reasons. First, appending to the end of a file is the fastest and safest kind of disk write — you can never corrupt existing data by adding after it. Second, rewriting a whole file on every change would be catastrophically slow and, worse, a crash mid-rewrite could destroy the old copy too. The same principle powers filesystem journaling (ext4, NTFS), database redo logs, and the replication logs of Raft and Paxos clusters.
Log-structured storage — the general name for this school of design: treat storage as an ever-growing log of changes rather than a structure edited in place. It trades some read-side complexity and periodic cleanup (compaction, §2.8) for write speed and crash safety. kvstore, Redis's AOF, Bitcask, LSM-tree engines (§4.4), and even SSD firmware internals are all log-structured.

A subtle but crucial property of the log: it is a history, not a snapshot. If you set name=Alice, then name=Bob, the log contains both records. The current state — name=Bob — emerges by reading the history in order and letting later entries win. This “last write wins” replay rule is what lets a log overwrite without ever editing.

The same logic explains something that surprises many people: deleting a key adds bytes to the file. There is no way to reach back and erase the old “set” records — the log is append-only — so a delete is recorded as one more entry in the history: “as of now, this key is gone.”

Tombstone — the storage-engineering name for a logged delete: a record that marks a key dead rather than physically removing it. During replay, a tombstone erases the key from the in-memory map; during compaction, the tombstone and every older record for that key are finally dropped together. Cassandra, RocksDB, and Bitcask all use exactly this term.

2.5 Torn writes — when a crash cuts a record in half

Torn write — a record that a crash or power cut interrupted partway through, leaving only some of its bytes on disk. The tail of the log after a crash may contain half a record — or a full record whose bytes were scrambled.

Recovery must never trust the tail of the log blindly. kvstore handles this two ways: it stops replaying at the first record that is incomplete (a “short read”), and it verifies every record's checksum (next section). It then truncates the file back to the last good record, so future appends land on a clean boundary instead of being stranded after garbage.

Notice a quiet gift of the append-only design here: damage from a crash can only ever be at the end of the file. Since existing bytes are never rewritten, records that were fully synced in the past cannot be harmed by a crash today. A store that edited its file in place would enjoy no such guarantee — a crash mid-edit could corrupt data written months ago, anywhere in the file. Append-only logging converts “corruption could be anywhere” into “corruption is only at the tail, where we know to look”. (One thing kvstore deliberately does not assume: that disks write any particular chunk — a 512-byte sector, say — atomically. Some do, some don't; the CRC makes the question irrelevant, because a record is trusted only if every one of its bytes checks out.)

2.6 Checksums (CRC32) — catching corruption

Checksum — a short number computed from a block of bytes, designed so that if even one bit of the block changes, the recomputed number will almost certainly differ. CRC32 (cyclic redundancy check, 32-bit) is a classic, fast checksum used by ZIP files, Ethernet, and PNG images.

Build the idea up in three steps. Step 1 — parity: the simplest integrity check is to store one extra bit saying whether the data has an even or odd number of 1-bits; flip any single bit and the parity no longer matches. Cheap, but blind to two flips. Step 2 — sums: add all the bytes up and store the total; better, but reordered or offsetting changes can slip through. Step 3 — CRC: treat the whole message as one giant number and take its remainder when divided by a carefully chosen constant (the “polynomial” — for CRC32, the famous 0xEDB88320). The division mixes every input bit into every output bit, so any single-bit flip, any burst of errors up to 32 bits, and the overwhelming majority of larger corruptions change the result. That remainder is the checksum.

Every record kvstore writes ends with a CRC32 of all the record's preceding bytes. During recovery, the CRC is recomputed and compared with the stored one. A mismatch means the record was torn by a crash or silently corrupted on disk (“bit rot” — storage media really do occasionally flip bits). Either way, the record is rejected rather than loaded as garbage.

Checksum vs. hash vs. cryptographic hash — three cousins, often confused. A checksum (CRC32) detects accidental corruption, fast. A hash function (std::hash, §2.11) spreads keys evenly across buckets, fast, with no integrity promise. A cryptographic hash (SHA-256) resists deliberate forgery, but is ~50× slower. kvstore needs only the first two: disks fail by accident, not malice.
Why not just trust the disk?
Because at scale, disks lie. Consumer SSDs have error rates around one undetected bad bit per ~1014 bits read. A database that loads whatever bytes it finds will eventually serve corrupted data with a straight face. The CRC turns silent corruption into a detected, contained event.

2.7 Recovery (replay) — rebuilding memory from the log

Recovery / replay — on startup, reading the log from the beginning, one record at a time, and re-applying each one to the in-memory map — re-doing history to arrive back at the present.

If the log says “set a=1, set b=2, delete a, set b=3”, then after replay memory contains exactly {b: 3}. Note that later records override earlier ones — this is why the log can simply append an overwrite instead of editing old data. Replay stops at the first incomplete, unknown, or checksum-failing record, and everything before that point is trusted.

Two properties make replay trustworthy. First, it is deterministic: the same log always rebuilds the same map, no matter when or on what machine it is replayed — there is no randomness and no dependence on timing. Second, applying a record is idempotent — a fancy word for “doing it twice is the same as doing it once”. “Set a=1” leaves a at 1 whether applied once or five times; the same goes for a delete. Together these mean recovery needs no cleverness and no bookkeeping about “how far did I get last time” — just start at byte zero and march forward. Simple procedures are the ones you can trust to run correctly on the worst morning of your life, right after a production crash.

2.8 Compaction — garbage collection for the log

Compaction — rewriting the log so it contains only the current value of each live key, dropping every overwritten, deleted, and expired record. It is garbage collection for on-disk data.

An append-only log never forgets: overwrite a key 1,000 times and the log holds 1,000 records for it. Compaction fixes this: write all live entries to a fresh temporary file, fsync it, then atomically rename it over the old log. If a crash happens at any point, either the old complete log or the new complete log exists — never a half-and-half mixture.

Write amplification — the ratio of bytes physically written to bytes of useful data stored. If you store 1 MB of live data but the log plus compaction rewrites cost 3 MB of disk writes, the amplification is 3×. Every log-structured system pays this tax; tuning when to compact is the balancing act between disk space (compact often) and write amplification plus pause time (compact rarely). kvstore leaves the timing to the caller — real engines trigger it automatically on thresholds.
Why is compaction the hardest thing in this codebase?
Because it must rewrite the store's single source of truth while the store is live, without losing a concurrent write, without a reader noticing, and while remaining crash-safe at every instant. Notice the recurring recipe, used by everything from package managers to firmware updaters: build the replacement completely off to the side, make it durable, then swap it in with one atomic operation. Never edit the real thing in place.
Atomic operation — a step that either fully happens or does not happen at all, with no observable in-between state. The POSIX rename() system call is atomic: the filename points to the old file, and then it points to the new file, and there is no instant where it points to nothing or to half of each.

2.9 Threads, race conditions, and mutexes

Thread — an independent line of execution inside one program. A program with 4 threads is doing 4 things literally at the same time (on 4 CPU cores). Threads share the same memory, which is both their superpower and their danger.
Process vs. thread — a process is one running program: the OS gives it its own private memory, its own file descriptors, its own identity. Run the same program twice and you get two processes that cannot see each other's variables at all. Threads live inside a process and share all of its memory. The distinction decides which tool coordinates whom: a mutex lives in memory, so it can only coordinate threads within one process; two separate processes can't even see each other's mutexes. Coordinating processes requires something both can reach — like a lock attached to a file (§2.16). kvstore needs both: mutexes for its threads, a file lock against other processes.
Race condition — a bug where the result depends on the unpredictable timing of two threads touching the same data. Example: two threads both run counter = counter + 1 at once; both read 5, both write 6, and one increment is silently lost. Race conditions are nightmarish because they strike rarely and randomly.
Mutex (mutual exclusion lock) — an object only one thread can “hold” at a time. A thread locks the mutex, touches the shared data, and unlocks it; any other thread trying to lock it meanwhile is paused until it is free. Whatever a mutex guards is therefore touched by one thread at a time — no races.
Why not just use one big mutex for everything?
Correct, but slow: every operation would wait in a single line, and 8 CPU cores would perform like 1. The next two ideas are the classic fixes.

Mutexes protect regions of code; sometimes you only need to protect a single variable, and there is a lighter tool for that:

Atomic variable (std::atomic) — a variable the CPU itself guarantees to read, write, or update in one indivisible hardware step, with no lock at all. The broken counter = counter + 1 example becomes correct as counter.fetch_add(1): the read-modify-write happens as one instruction no other core can interleave with. kvstore uses an atomic bool to ensure only one compaction runs at a time, and the test suite uses atomic counters. Atomics also let you specify a memory order — how much cross-thread ordering you need. The default (seq_cst) is strongest and safest; memory_order_relaxed, which the test counters use, promises only atomicity, which is all a statistics counter needs and is cheaper on weakly-ordered CPUs like ARM.

2.10 Shared vs. exclusive locks — letting readers run in parallel

Shared / exclusive lock (reader–writer lock, C++'s std::shared_mutex) — a smarter mutex with two modes. A shared lock can be held by any number of readers at once (reading cannot corrupt anything). An exclusive lock is for writing: one holder only, and it excludes all readers too.

Most real workloads read far more than they write. Letting unlimited concurrent readers proceed — and only serializing the writes — is a huge win. In kvstore, Get, Range, and Size take shared locks; Set and Delete take exclusive ones.

Why would anyone ever use a plain mutex, then? Because reader–writer locks are not free: they must count the active readers, which makes each lock/unlock slightly more expensive, and a steady stream of readers can make a writer wait a long time for its exclusive turn (“writer starvation” — implementations vary in how fairly they handle this). The rule of thumb: shared locks win when the protected work is long and read-mostly — exactly a hash-map lookup serving many readers — and a plain mutex wins for short, write-heavy critical sections, which is exactly why the WAL, where every operation is a write, uses one. kvstore uses each tool where it fits.

2.11 Sharding (lock striping) — splitting the keyspace 16 ways

Shard — one slice of the data. kvstore splits keys across 16 independent maps, each with its own lock, chosen by hash(key) % 16. A thread writing "apple" and a thread writing "zebra" almost certainly touch different shards and never wait on each other. This pattern is called lock striping.
Hash / hash map — a hash function turns any string into a pseudo-random number; a hash map uses that number to find where a key's value is stored, making lookups nearly instant regardless of size. C++'s std::unordered_map is a hash map. Taking the hash % 16 assigns every key a stable home shard.
Contention — the situation where multiple threads want the same lock at the same moment; all but one must wait. Contention, not locking itself, is what kills scalability — an uncontended lock costs nanoseconds. Sharding works by converting one highly-contended lock into 16 rarely contended ones: with 4 threads spread over 16 shards, the chance that any two collide on the same shard at a given instant is small, so most operations never wait at all.
Why 16?
A power of two comfortably larger than typical core counts. More shards = less contention but more memory overhead; 16 is a sensible teaching default. Java's ConcurrentHashMap and many kernel structures use exactly this technique. One caveat worth knowing: sharding a hash map means keys are scattered pseudo-randomly, so sorted scans (Range) must visit every shard and sort afterwards — the price of fast point lookups. Engines that need fast sorted scans use ordered structures (B-trees, skip lists) instead; §4.4 returns to this trade-off.

2.12 Lock ordering — how to never deadlock

Deadlock — thread A holds lock 1 and waits for lock 2, while thread B holds lock 2 and waits for lock 1. Both wait forever. The standard cure: every thread acquires locks in the same globally-agreed order.

kvstore's rule: always take the WAL mutex first, then a shard lock — never the reverse. Every code path follows it, so the deadly cycle can never form.

Why does a fixed order make deadlock impossible, rather than just unlikely? Picture the waiting threads as arrows: an arrow points from the lock a thread holds to the lock it wants. A deadlock is a cycle of arrows — A waits for B while B waits for A. If every thread acquires locks in one agreed order (WAL mutex ranked before shard locks), then every arrow points strictly “up the ranking”, and arrows that only ever point upward can never loop back around into a cycle. This is a proof, not a heuristic — which is what you want, because deadlocks, like race conditions, are far too rare and timing-dependent to find by testing.

2.13 TTL and lazy expiry — keys that clean up after themselves

TTL (time-to-live) — an optional lifespan on a key. SetWithTtl("session", data, 3600) stores a key that acts deleted after one hour.
Lazy expiry — instead of a background thread scanning for expired keys (complex, wasteful), expired keys are simply hidden whenever they are read, and physically removed later during compaction. The user-visible behaviour is identical; the implementation is far simpler. Redis uses this same strategy.
Sentinel value — a reserved special value meaning “none”. kvstore stores the expiry as an absolute Unix timestamp, and uses 0 as the sentinel for “never expires” (no real expiry is at timestamp 0, which was midnight, January 1st, 1970).
Unix timestamp — the number of seconds elapsed since midnight UTC on January 1st, 1970 (“the epoch”). It is computing's shared clock: a single 64-bit number, timezone-free, trivially comparable. Storing the absolute expiry moment (rather than “30 seconds from now”) is what makes TTLs survive restarts: the deadline in the log means the same thing whenever it is replayed. One honest caveat: the system clock can jump (a user changes it, NTP corrects it), which shifts pending expiries with it — an accepted limitation shared by most TTL systems.

2.14 Serialization and endianness — turning data into portable bytes

Serialization — converting in-memory data (numbers, strings, structs) into a flat sequence of bytes that can be written to a file, and converting those bytes back on read.
Endianness — the order a CPU stores a multi-byte number's bytes in. The number 0x11223344 is stored as 44 33 22 11 on a little-endian machine (x86, most ARM) but 11 22 33 44 on a big-endian one (some network gear, older PowerPC). If you write raw memory to a file on one kind of machine and read it on the other, every number is scrambled.

kvstore explicitly encodes every integer in the log in little-endian byte order, byte by byte, regardless of what CPU it runs on. The log file is therefore portable: written on a PC, readable on a big-endian router. (On x86/ARM the encoded bytes are identical to raw memory, so this safety costs nothing.) This mirrors how network protocols pin down a single “wire format”.

The deeper lesson generalizes beyond endianness: never write raw memory to a file. A struct's in-memory layout depends on the CPU's byte order, the compiler's padding between fields, and even compiler flags — none of which you control years later when someone opens the file on different hardware. A file format must be defined as bytes, precisely, the way §3.3 defines kvstore's record: this field is exactly 4 bytes, low byte first, at this offset. (Why little-endian rather than big? Pure pragmatism: virtually every CPU the file will ever meet — x86, mainstream ARM — is little-endian, so the common case costs zero conversion work. Network protocols historically chose big-endian; either works, as long as the choice is written down and enforced.)

2.15 File descriptors and POSIX — talking to the OS directly

POSIX — the standard Unix/Linux system-call interface: open, write, fsync, rename, flock, and friends. These are the raw doors into the operating system, one level below C++'s comfortable fstream.
File descriptor (fd) — a small integer the OS hands you when you open a file; you pass it to every subsequent call about that file. kvstore uses raw fds for its log because durability requires calls that fstream simply does not offer: fdatasync (force to disk) and ftruncate (roll back a partial write).

A good mental model: fstream is a comfortable wrapper around a file descriptor. It adds its own buffering and pleasant C++ syntax, and for everyday file work it is the right choice — kvstore itself uses an ifstream for reading during recovery, where comfort is fine. But the wrapper hides the fd, and the durability-critical calls (fdatasync, ftruncate, flock) take an fd. So on the write path, where every guarantee lives, kvstore drops down to the raw POSIX layer. There is one more subtlety the raw layer exposes: creating a file only durably exists once its parent directory is also fsynced — a directory is itself a small file mapping names to files, with its own cache. kvstore does exactly this (SyncParentDir in the walkthrough) after creating or renaming the log — a detail even experienced programmers miss.

2.16 Advisory file locks — one process at a time

Advisory lock (flock) — a lock attached to a file that cooperating processes check before using it. “Advisory” means the OS does not force anyone to obey it — but every well-behaved program (like kvstore) checks first.

Why it matters: imagine two copies of your program opening the same store. Both would append to the same log with no coordination, interleaving and corrupting each other's records. kvstore prevents this by taking an exclusive advisory lock on a .lock file at startup; a second process gets a clean error (“store is locked by another process”) instead of a corrupted database. SQLite, LevelDB, and virtually every embedded database do exactly this.

A pleasant property of flock: the lock belongs to the open file descriptor, not to the file's contents. If the process crashes, the OS closes its descriptors and thereby releases the lock automatically. There is no “stale lock” problem to clean up — unlike naive schemes that create a lock file and delete it on exit, which break the first time an exit isn't clean.

2.17 The honest trade-offs — what this design gives up

Intermediate systems thinking means knowing what a design doesn't do. kvstore's choices are principled, and each has a cost. Understanding these five is understanding the design:

  • One fsync per write. Durability costs ~1 ms of disk flush per operation, and all writers serialize on one WAL mutex — so write throughput is capped by the disk, not the CPU, no matter how many threads you add. Production engines soften this with group commit: batch many pending writes into one fsync, amortizing the cost. (A natural extension exercise for this codebase.)
  • No multi-key transactions. Each operation is atomic and durable by itself, but there is no way to make “debit account A, credit account B” a single all-or-nothing unit. Full transaction support needs undo/redo logging or snapshots — a large step up in complexity.
  • The dataset must fit in RAM. Every key and value lives in the in-memory maps; the disk is a recovery log, not an overflow area. Fine for caches and config stores; wrong for a terabyte of data. Engines like RocksDB keep only an index in memory and read values from disk (§4.4).
  • Scans are O(n). Range visits every entry in every shard and sorts the survivors. Hash maps have no order; engines built for range queries use ordered structures instead.
  • Recovery time grows with the log. Startup replays every record since the last compaction. Compact rarely and a restart can take a while — another reason real engines automate compaction.

Part 3 — The Architecture

3.1 The two layers

kvstore is two layers glued together by one golden rule:

  • The in-memory index — 16 shards, each a std::unordered_map<string, Entry> guarded by its own reader–writer lock. This is where every read is answered, at RAM speed. It is lost on every shutdown or crash — and that is fine, because of the second layer.
  • The on-disk write-ahead log (db.wal) — the durable source of truth. Every change is appended and fsynced here first. On startup, replaying it rebuilds the in-memory index exactly.
The golden rule
A change hits the disk log (fsynced) before the in-memory map is updated, and both steps happen while one lock (wal_mutex_) is held. Consequence: memory never claims something the disk doesn't know, the log's record order always matches the order changes became visible, and a crash at any instant leaves a log that replays to a correct state.

3.2 The write path and read path

WRITE PATH READ PATH ---------- --------- Set / SetWithTtl / Delete Get / Range / Size / Items | | v v lock wal_mutex_ lock shard (shared mode) | | serialize record v append to db.wal look up in unordered_map fdatasync (now durable) | | hide if expired (TTL) v | lock shard (exclusive) v update unordered_map return the value | v unlock everything, return true 16 shards, each = { shared_mutex, unordered_map<string, Entry> } which shard? -> hash(key) % 16 STARTUP : lock db.lock -> replay db.wal (CRC-checked) -> truncate torn tail COMPACTION: live keys -> db.wal.tmp -> fdatasync -> atomic rename -> db.wal

Notice the asymmetry: reads never touch the disk or the WAL mutex at all — they take one shared shard lock and read RAM. This is why reads scale nearly linearly with cores. Writes pay the full durability price: serialize, append, fsync, then update memory.

3.3 The on-disk record format

Every change becomes one binary record in the log, laid out as:

[ type:1 ][ key_len:4 ][ value_len:4 ][ key bytes ][ value bytes ][ expires_at:8 (kSetTtl only) ][ crc32:4 ]
  • type (1 byte) — what kind of change: 1=Set, 2=Delete, 3=SetTtl.
  • key_len / value_len (4 bytes each, little-endian) — how many bytes of key and value follow. Lengths let the reader know exactly where each field ends without any separators.
  • key / value bytes — the raw data. A Delete record carries no value.
  • expires_at (8 bytes, little-endian, only for SetTtl) — the absolute Unix timestamp when the key dies.
  • crc32 (4 bytes, little-endian) — checksum over every preceding byte of the record.

This is fixed-width binary framing: compact (no JSON overhead), fast to parse, self-checking, and — because every integer is written in explicit little-endian order — identical on every CPU architecture.

Why lengths up front, rather than a separator between fields (the way CSV uses commas)? Because separators create the escaping problem: if a comma splits fields, what happens when a value contains a comma? Every delimiter-based format needs escape rules, and escape rules breed bugs and parsing ambiguity. Length-prefixed framing has no such problem — a key or value may contain any bytes whatsoever, including zeros and newlines, because the reader never searches for a boundary; it is told exactly how many bytes to take. The lengths also give recovery an early sanity check: a length exceeding the caps (kMaxKeyLen, kMaxValueLen) proves the header is garbage before a single payload byte is read. This is the same reason network protocols (TCP options, TLS records, protobuf) are length-prefixed rather than delimiter-based.

A worked example, byte by byte

Let's make it concrete. Suppose you call Set("cat", "meow"). The key is 3 bytes, the value is 4 bytes, so the record is 1 + 4 + 4 + 3 + 4 + 4 = 20 bytes on disk. Here is every one of them (hex on the left, meaning on the right):

01 type = 1 (kSet) 03 00 00 00 key_len = 3 (little-endian: low byte first) 04 00 00 00 value_len = 4 63 61 74 "cat" (ASCII: c=0x63, a=0x61, t=0x74) 6d 65 6f 77 "meow" 55 ba 87 3d crc32 of the 16 bytes above = 0x3d87ba55 (little-endian)

Read the 03 00 00 00 line carefully — that is little-endian in action: the number 3 stored lowest-byte-first. A big-endian machine writing raw memory would have produced 00 00 00 03, which a little-endian reader would decode as 50,331,648 — and instantly reject via the 1 MiB length cap. This is exactly the corruption class the explicit encoding (§2.14) eliminates. Now recovery in reverse: read 01 (a known type), read the lengths (3 and 4 — plausible), read 3 + 4 payload bytes, read the CRC, recompute it over the first 16 bytes, compare. Match → apply cat=meow to shard hash("cat") % 16. Mismatch → stop, truncate. Every record in every kvstore log follows this exact dance.

The life of one key — from set to compaction

Now zoom out from one record to one key's whole lifetime, and watch the log and the map diverge and reconcile. Suppose you set cat=meow, later change it to cat=purr, and finally delete it:

action log on disk (grows only) in-memory map ------ ------------------------ ------------- Set(cat, meow) [set cat=meow] {cat: meow} Set(cat, purr) [set cat=meow][set cat=purr] {cat: purr} Delete(cat) [set cat=meow][set cat=purr][del cat] {} ...crash + restart: replay all 3 records in order... {} <- same state! Compact() (empty — no live keys to keep) {}

Every row illustrates a concept from Part 2. The overwrite does not touch the first record — it appends, and “last write wins” (§2.4) makes the map show purr. The delete adds a third record — the tombstone (§2.4) — while the map shrinks; log size and map size have now fully parted ways (three records on disk, zero keys in memory). Replay after a crash walks the same history and lands on the same empty map, because replay is deterministic (§2.7). And compaction (§2.8) finally reconciles the two: it writes only what the map holds — nothing — so all three records, tombstone included, vanish together. The log is a diary; the map is the present moment; compaction is rewriting the diary to say only how things ended up.

3.5 Failure handling — the part that separates real engines from toys

  • Write fails halfway? The log is ftruncated back to its previous end, so the tail stays on a clean record boundary, and the caller gets false. Memory is never touched.
  • fsync fails? Same rollback, same false. A write is never acknowledged unless it is physically on disk.
  • Crash mid-write? Recovery finds a short or CRC-failing record at the tail, stops there, and truncates the garbage off.
  • Crash mid-compaction? The atomic rename means either the old or the new log exists in full. The temp file, if orphaned, is simply overwritten next time.
  • Compaction can't reopen the new log? The store remembers the file descriptor is closed and retries the open on the next write, instead of failing forever.
  • Second process opens the store? Refused cleanly at the lock file, before it can touch anything.

3.7 The startup sequence — and the memory bill

One path remains: what happens inside KVStore store("my.db") before the constructor returns. The order is rigid, and each step exists to protect the ones after it:

  1. Create the parent directory if the path needs one — everything else needs somewhere to live.
  2. Acquire the process lock (§2.16) — before touching any data file. If another process owns the store, the constructor throws here, having modified nothing. Locking first means the replay and truncation below can never race against another process's appends.
  3. Replay the WAL (§2.7) — rebuild the in-memory shards record by record, CRC-checking each.
  4. Truncate the torn tail (§2.5) — if replay stopped early, cut the file back to the last good record, so the garbage can never sit in the middle of the log once new appends follow it.
  5. Open the WAL for appending — only now, with the file known-clean, is the append fd opened. The constructor returns; the store is live.

Step 2 before step 3 and step 4 before step 5 are the load-bearing orderings — swap either pair and you get, respectively, two processes replaying/appending simultaneously, or fresh records appended after undetected garbage.

Startup is also the honest place to present the memory bill. Every live key and value is in RAM, and the containers add bookkeeping on top of the raw bytes: a std::string carries a pointer, size, and capacity (and stores short strings inline), and each unordered_map node adds hash-bucket linkage — typically 50–100 bytes of overhead per entry beyond the key and value themselves. A million entries of 20-byte keys and 100-byte values is ~120 MB of raw data but closer to ~200 MB resident. Rule of thumb: budget roughly twice the raw data size, and remember replay must also read the entire log before the store opens — both are reasons the §2.17 “fits in RAM” trade-off deserves respect.

4.2 Where you would use something like kvstore

  • Caches with expiry — session tokens, rate-limit counters, cached API responses that should vanish after N seconds: the TTL feature is purpose-built for this.
  • Local durable state for a service — a daemon that must remember a little state across restarts without dragging in a database server.
  • Game saves and settings — data that must survive the console losing power mid-save.
  • IoT and embedded devices — sensor calibration, device config on a router or thermostat, where every design constraint below applies.

And, just as importantly, where you would not use it — each “no” traces straight back to a trade-off from §2.17: data larger than RAM (the map holds everything in memory), multiple programs needing the same store at once (the process lock admits exactly one), workloads needing multi-key transactions (each operation is atomic only by itself), or heavy sorted-range queries over millions of keys (hash-map scans are O(n)). Knowing a tool's “no” list is what separates choosing a design from merely liking one.

4.3 Why this design fits embedded systems especially well

  • Compact binary serialization — fixed-width framing with a trailing checksum is exactly how embedded protocols (CAN bus, Modbus, BLE packets) are encoded: small, fast, predictable, self-checking.
  • Bounded, defensive parsing — kMaxKeyLen/kMaxValueLen cap what recovery will believe from a length field. On a memory-limited device, one corrupt byte must not trigger a 256 MB allocation. The write path enforces the same caps, so it can never produce a record recovery would reject.
  • Flash-friendly appends — append-only logging suits NOR/NAND flash and SD cards, where in-place rewrites cause wear. Embedded filesystems (LittleFS, SPIFFS) are log-structured for the same reason.
  • Power-loss resilience — brown-outs are routine for battery devices. The fsync-before-acknowledge write path plus torn-record recovery is the standard “brown-out safe” pattern; the fsynced temp file + atomic rename in compaction mirrors dual-bank A/B firmware updates.
  • Deterministic resources — zero third-party libraries, a compile-time shard count (constexpr, std::array), no unbounded background threads. Predictable, statically sized resource use is a hard requirement in real-time systems.
  • Portable log format — the explicit little-endian encoding means an SD card written by an ARM device can be read on any workstation for debugging.

4.4 From kvstore to RocksDB — what production engines add

kvstore is a faithful miniature of a production storage engine's core. If you understand it, here is the remaining staircase to a real engine like RocksDB, one step at a time — each step solving a limitation from §2.17:

Group commit — instead of one fsync per write, collect all writes that arrive within a window and flush them with a single fsync, sharing the ~1 ms cost across dozens of operations. Same durability, order-of-magnitude more write throughput. The first upgrade any real engine makes. SSTable (sorted string table) — an immutable file of key–value pairs stored in sorted order. Because it is sorted, a range scan is a sequential read, and a lookup is a binary search — fixing the “hash maps can't scan” problem. Because it is immutable, it needs no locks and can be checksummed once. LSM-tree (log-structured merge tree) — the full architecture: recent writes live in a small in-memory sorted map (backed by a WAL — exactly kvstore's trick); when it fills, it is flushed to disk as an SSTable; background compaction repeatedly merges SSTables into bigger, older ones. The dataset no longer needs to fit in RAM — RAM holds only the newest slice, and reads consult the SSTable stack. RocksDB, LevelDB, Cassandra, and ScyllaDB are all LSM engines. Bloom filter — a tiny probabilistic bitmap that answers “is this key definitely not in this SSTable?” in nanoseconds, letting reads skip most files without touching the disk. The classic cure for LSM read amplification. MVCC / snapshots (multi-version concurrency control) — keep multiple timestamped versions of values so readers see a frozen, consistent snapshot while writers proceed — no reader–writer blocking at all, and the foundation for multi-key transactions.

Every one of these builds directly on the concepts you now know: the WAL is still there, the CRCs are still there, compaction is still there — just generalized. That is why this project is worth studying: the hard ideas in a 100,000-line engine are the same ones in these 700 lines.

4.5 The other staircase — going distributed

§4.4 scaled kvstore down the storage stack: bigger-than-RAM data on one machine. The other axis is more machines, and it is where the famous cloud databases live. Two new failure modes force it: a single machine can die taking its disk with it, and a single machine has a ceiling on traffic and capacity. The remedies are three ideas — and each one, satisfyingly, is a concept from Part 2 wearing a bigger coat:

Replication — keep full copies of the data on several machines, so losing one loses nothing. The standard mechanism: a leader machine appends each write to its WAL, then streams the same log records to follower machines, which replay them — exactly kvstore's recovery (§2.7), just over a network. The WAL literally becomes the replication protocol. This works only because replay is deterministic: the same log produces the same state on every machine. PostgreSQL streaming replication and Redis replicas are precisely this. Partitioning — kvstore's hash(key) % 16 (§2.11), with machines instead of shards: hash(key) now chooses which server owns the key, so capacity and traffic spread across the fleet. One refinement is needed — with naive % N, adding a server reshuffles nearly every key; consistent hashing arranges servers on a ring so that adding one moves only its small slice. Amazon's Dynamo paper made this famous; Cassandra and DynamoDB are its descendants. Consensus (Raft, Paxos) — replication's hard edge case: if the leader dies mid-stream, which follower's log is the truth, and who becomes the new leader? Consensus protocols have the machines vote so that a majority always agrees on a single, identical log — the lock-ordering discipline of §2.12 writ large: a global agreement that makes a whole class of disaster impossible rather than unlikely. etcd — the store Kubernetes trusts with an entire cluster's state — is Raft consensus wrapped around a kvstore-like WAL + in-memory map.

Notice what did not change on the way up either staircase: an append-only log of records, replayed deterministically, checksummed against corruption, compacted to bound growth. From a 700-line class to a planet-scale database, that core is the same — which is the strongest argument that it is the part worth learning first.

        // precomputed crc32 table
        struct Crc32Table {
            std::uint32_t v[256];
            constexpr Crc32Table() : v{} {
                for (std::uint32_t i = 0; i < 256; ++i) {
                    std::uint32_t c = i;
                    for (int k = 0; k < 8; ++k) {
                        c = (c & 1u) ? (0xEDB88320u ^ (c >> 1)) : (c >> 1);
                    }
                    v[i] = c;
                }
            }
        };
        constexpr Crc32Table kCrc32Table{};

        std::uint32_t Crc32(const void* data, std::size_t len) {
            const auto* p = static_cast<const std::uint8_t*>(data);
            std::uint32_t crc = 0xFFFFFFFFu;
            for (std::size_t i = 0; i < len; ++i) {
                crc = kCrc32Table.v[(crc ^ p[i]) & 0xFFu] ^ (crc >> 8);
            }
            return ~crc;
        }

This is the standard IEEE 802.3 CRC32 — the same one used by ZIP and PNG. The clever part: because the constructor is constexpr, the compiler computes the whole 256-entry lookup table at build time and embeds it in the binary as read-only data. At runtime, checksumming costs one table lookup and two XORs per byte — roughly 8× faster than computing bit-by-bit. 0xEDB88320 is the standard reversed CRC32 polynomial; the leading ~/0xFFFFFFFF pre- and post-inversion is part of the specification so that runs of zeros do not checksum to zero.

        void AppendU32Le(std::string& buf, std::uint32_t v) {
            const char b[4] = {
                static_cast<char>(v & 0xFFu),
                static_cast<char>((v >> 8) & 0xFFu),
                static_cast<char>((v >> 16) & 0xFFu),
                static_cast<char>((v >> 24) & 0xFFu),
            };
            buf.append(b, sizeof(b));
        }

        void AppendI64Le(std::string& buf, std::int64_t v) {
            const auto u = static_cast<std::uint64_t>(v);
            char b[8];
            for (int i = 0; i < 8; ++i) {
                b[i] = static_cast<char>((u >> (8 * i)) & 0xFFu);
            }
            buf.append(b, sizeof(b));
        }

        std::uint32_t LoadU32Le(const char* p) {
            const auto* u = reinterpret_cast<const unsigned char*>(p);
            return static_cast<std::uint32_t>(u[0]) |
                   (static_cast<std::uint32_t>(u[1]) << 8) |
                   (static_cast<std::uint32_t>(u[2]) << 16) |
                   (static_cast<std::uint32_t>(u[3]) << 24);
        }

        std::int64_t LoadI64Le(const char* p) {
            const auto* u = reinterpret_cast<const unsigned char*>(p);
            std::uint64_t v = 0;
            for (int i = 0; i < 8; ++i) {
                v |= static_cast<std::uint64_t>(u[i]) << (8 * i);
            }
            return static_cast<std::int64_t>(v);
        }

These four functions are the portability layer (recall endianness from §2.14). Instead of copying a number's raw memory to disk — whose byte order depends on the CPU — they build the bytes explicitly. AppendU32Le peels off the lowest byte first (v & 0xFF), then each next byte by shifting right 8 bits at a time: least-significant byte first, which is little-endian, by construction, on any machine. The Load… functions do the mirror image: take byte 0 as the low byte, shift each next byte into place, and OR them together. The 64-bit versions route through uint64_t because bit-shifting signed negative numbers is implementation-defined in C++ — converting to unsigned first makes it exact and portable.

        bool WriteFully(int fd, const char* data, std::size_t len) {
            std::size_t written = 0;
            while (written < len) {
                const ssize_t n = ::write(fd, data + written, len - written);
                if (n < 0) {
                    if (errno == EINTR) {
                        continue;
                    }
                    return false;
                }
                if (n == 0) {
                    return false;  // no progress, don't spin
                }
                written += static_cast<std::size_t>(n);
            }
            return true;
        }

    bool KVStore::AppendRecordLocked(RecordType type, const std::string& key,
                                    const std::string& value, std::int64_t expires_at) {
        // reject oversized fields, recovery would treat them as corrupt
        if (key.size() > kMaxKeyLen) {
            return false;
        }
        if (type != RecordType::kDelete && value.size() > kMaxValueLen) {
            return false;
        }

        const std::string record = SerializeRecord(type, key, value, expires_at);

        // reopen if a failed compaction left the fd closed
        if (wal_fd_ < 0 && !OpenWalLocked()) {
            return false;
        }

        // tail offset, for rollback on failure
        const off_t before = ::lseek(wal_fd_, 0, SEEK_END);
        if (before < 0) {
            return false;
        }

        if (!WriteFully(wal_fd_, record.data(), record.size())) {
            if (::ftruncate(wal_fd_, before) != 0) {}  // roll back partial write
            return false;
        }

        // fsync before the record is visible in memory
        if (::fdatasync(wal_fd_) != 0) {
            if (::ftruncate(wal_fd_, before) != 0) {}
            return false;
        }
        return true;
    }

The heart of durability, in five steps. (1) Validate: refuse keys/values larger than the caps — writing one would poison the log, because recovery would treat its header as corrupt and stop there. (2) Self-heal: if a previous failed compaction left the descriptor closed, try to reopen it now instead of failing forever. (3) Bookmark: lseek(…, SEEK_END) records the current end of the file. (4) Write: append the full record. (5) Sync: fdatasync forces it onto the physical disk. If step 4 or 5 fails, ftruncate(fd, before) rolls the file back to the bookmark, so a half-written record never remains, and the caller receives false with memory untouched. A write is acknowledged only when it is physically durable.

    std::vector<KeyValue> KVStore::Range(const std::string& start, const std::string& end) const {
        std::vector<KeyValue> result;
        for (const auto& shard : shards_) {
            std::shared_lock lock(shard.mutex);
            for (const auto& [key, entry] : shard.data) {
                if (IsExpired(entry.expires_at)) {
                    continue;
                }
                if (key < start) {
                    continue;
                }
                if (!end.empty() && key >= end) {
                    continue;
                }
                result.push_back(KeyValue{key, entry.value});
            }
        }
        std::sort(result.begin(), result.end(),
                [](const KeyValue& a, const KeyValue& b) { return a.key < b.key; });
        return result;
    }

The scanning trio. Size walks all shards under shared locks (one at a time, so other shards stay fully available) counting non-expired entries — the count always matches what Get would report. Items is just Range with empty bounds. Range collects entries that are live, at or after start, and before end (an empty end means unbounded — the half-open [start, end) convention used across computing). Hash maps store keys in no particular order, so the merged result is sorted at the end.

compare_exchange_strong is an atomic instruction that checks and sets a flag in one indivisible CPU step: “if the flag is false, set it true and tell me I won.” If another thread already started compacting, this call loses and returns early — two simultaneous compactions would fight over the temp file. Phase one of compaction: build the replacement log. A temp file is opened with O_TRUNC (clearing any leftover from an earlier crash). Every shard is walked under a shared lock — readers keep working throughout — and every live, non-expired entry is written as a fresh record using the very same SerializeRecord, so the new log has correct CRCs and format by construction. Expired entries are simply skipped: this is where lazy expiry finally reclaims disk space. The temp file is fsynced before the swap — renaming an un-synced file into place would be durability theater. On any failure, the temp file is deleted and the original log remains untouched.
